# Agent-loom Upgrade Plan
## Problem
You are a non-technical solo PM building AI-heavy consumer/enterprise products (multi-agent systems like aegis, mobile like prof-photon, local-first like Ember). agent-loom is your compensating layer for missing engineering judgment. Five challenges: (1) harnesses/multi-agent systems aren't self-improving and have no observability, and you can't judge if the eval suite is good enough; (2) no model-tier routing, so cheap models wreck complex tasks; (3) skills don't trigger reliably in Cursor; (4) no learnings from superpowers; (5) SDD and TDD aren't wired together.
## Current state (what research found)
* 109 skills, strong meta/security/eval/harness suites — but `harness-*`, `run-trace`, `fault-localize`, `eval-*` all target the *coding agent*, not your *shipped product's* agents. No skill instruments production agent tracing (Phoenix/OpenInference-style), and no GEPA-style runtime learning loop for shipped agents.
* No model-selection skill exists anywhere in the library (grep confirmed).
* Deferred item #10 (native per-tool adapters, incl. Cursor) is parked in `docs/memory/deferred.md` — its reopen trigger ("tool-specific routing friction") has now fired. Superpowers solves triggering with a session-start hook + a `using-superpowers` router meta-skill; agent-loom relies on AGENTS.md prose, which Cursor often ignores.
* obra/superpowers (~243k stars, MIT, v6.x): TDD with "delete code written before tests", systematic-debugging, verification-before-completion, subagent-driven development with two-stage review, writing-plans for "junior engineer with no judgment" — that last framing is exactly what low-tier models need.
* All skill work must route through the repo's own gates: `universal-skill-creator`, `learn-from-repo` + `secure-*`, `improve-skills`, `skill-deconflict`, `library-skill`, ≤200-line SKILL.md, L3 examples.
## Proposed changes — 6 phases (multi-session; each phase ends with library sync + memory checkpoint)
### Phase 1 — Trigger reliability (do first: multiplies everything else)
* Build a generator script that emits `.cursor/rules/agent-loom-routing.mdc` (alwaysApply rule with the routing table + User Entry Points distilled from `docs/SKILL-INDEX.md` and `.agents/ROUTING.md`), so Cursor always sees skill routing without relying on AGENTS.md pickup. Reopens deferred #10, Cursor adapter first.
* Adopt superpowers' pattern: a tiny always-loaded router artifact per host (Cursor rule now; Claude/Gemini command adapters stay deferred).
* Update `project-setup`, `retroactive-project-setup`, and `agent-loom-sync` to install/refresh the Cursor rule in consumer projects.
### Phase 2 — Model-tier routing (cheap, high leverage)
* New skill `model-selection` (via `universal-skill-creator`): a tier registry in `references/model-tiers.md` (editable as models change) + task-class→tier mapping + mandatory escalation rules (low-tier stuck in loop / repeated test failures / architectural decision needed → stop and escalate) + guardrails for low-tier execution (only run against a high-tier-written spec + tests; never let low tier make design decisions).
* Advisory, not automatic: harnesses like Cursor cannot switch models mid-run. The skill therefore (a) emits a model-plan table BEFORE execution begins, and (b) at each module boundary announces "next module → use tier X / model Y" so you switch manually. No skill ever assumes it can change the model itself.
* Correcting your tiering: Opus 4.8 and GPT-5.5 = high-cognition (architecture, foundations, planning, debugging gnarly issues). **Sonnet 5 is stronger than you think — high-mid, fine for most feature implementation.** GPT-5.4 = high-mid too. GLM-5.2 = mid (well-scoped implementation with tests as guardrails). Composer 2.5 = fast/low (small scoped edits, renames, boilerplate — never multi-file design work).
* Edit `implementation-plan` and `problem-to-plan`: every plan module/task gets a `model:` tier assignment; foundations/architecture tasks always pinned high-tier. The high-tier model writes the plan so each module is executable by the assigned tier (superpowers' "junior engineer" framing).
### Phase 3 — Agentic quality loop for shipped products (your biggest gap)
Three new skills (each ≤200 lines, via creator, deconflicted against `harness-evolution`/`run-trace`/`experimentation`):
* `agent-observability` — plain-language primer (what traces/spans/observability mean and why they matter, written for you) + workflow to instrument a product's agents with OpenTelemetry/OpenInference. NOT Phoenix-only: includes a free-tier-first backend decision table (Langfuse Cloud free tier, Phoenix Cloud free tier, LangSmith free tier, self-host-in-cloud as last resort — never on your laptop) and a plain-language architecture explainer (the backend is a separate managed service; your app just sends trace data to it over HTTPS; gotchas: never log secrets/PII into traces, sample to control cost). Wired into `agent-system-architecture` Step 4 and `setup-evaluation` as a check for agent-chain products.
* `agent-run-retro` — the interactive loop you asked for: after dev runs, interviews you via CLI (what went well/poorly, in plain language), drafts ranked hypotheses about what would most improve output quality/performance, designs n=1/n=2 experiments with clear success criteria, records results. Encodes your priority order quality > performance > cost with an explicit diminishing-returns stop rule. No experiments for their own sake — every experiment must name the outcome it should move.
* `runtime-learning-loop` — self-improvement for shipped agents, technique-agnostic (GEPA is one option, not the default; the skill's research pass surveys current alternatives and picks per project): traces → eval/judge scoring → improvement proposals → human approval gate → promote. Explicitly distinct from `harness-evolution` (which improves the coding agent).
* Autonomous experimentation: `agent-run-retro` + `runtime-learning-loop` design AND run experiments themselves — pre-declaring success definitions, guardrails, failure modes, stop conditions, and a cost/ROI kill-switch (stop when expected quality lift no longer justifies spend). You approve hypotheses and promotions; the machinery runs without you.
* Plus: targeted `improve-skills` pass with live research on the `eval-output` suite (rubric design, judge, pipeline) to answer "is my eval suite actually good" against current best practice.
### Phase 4 — Superpowers ingestion
* Run `learn-from-repo` on obra/superpowers with the full credibility + `secure-*` pipeline, then pairwise-compare against: `brainstorming`, `test-driven-development`, `debug-and-fix`, `code-review-crsp`, `incremental-implementation`, `implementation-plan`, `git-workflow-and-versioning`, `universal-skill-creator`. Merge craft where they win (expected: TDD hard gates, verification-before-completion, two-stage review, testing anti-patterns, plan-task granularity). Follows the proven addyosmani evolution model already in memory.
### Phase 5 — SDD × TDD unification
* Wire `feature-spec` Given/When/Then ACs to emit failing-test skeletons; `spec-driven-development` `/implement` enforces red-green per slice through `incremental-implementation` + `test-driven-development`; `spec-crosscheck` gains an AC↔test traceability check. Edits to existing skills only — no new skill.
### Phase 6 — Remaining audit gaps (queued, not this pass)
* `mobile-app-development` (React Native/Expo) and `mcp-server-authoring` — log to `deferred.md` with reopen triggers; build in a later session so this pass stays focused.
## Execution notes
* Portability is a hard requirement: every new skill and adapter must work in ANY project the `.agents` folder is copied into — derive state from `.agents/` contents and the consumer project's own `docs/`, never from agent-loom-only files. The Cursor rule generator reads `.agents/skills/` frontmatter directly (not agent-loom's `docs/SKILL-INDEX.md`) so it works after a bare folder copy.
* No child agents: the repo's own governance (sequential library-skill syncs to shared SKILL-INDEX/AGENTS.md/README, security gates) makes parallel writers conflict-prone; single-agent sequential execution per phase is safer and cheaper.
* Conventions preserved: ≤200-line bodies, depth in `references/`, L3 examples, P2 craft sections, changelog + memory checkpoints per phase, no direct SKILL.md writes.
* Suggested order 1→2→3→4→5 (4 and 5 can swap). Each phase is a natural session boundary with a handoff, so you can stop/resume without losing context.
* Token conservation: phases 1–2 are small; phase 3 is the largest; phase 4 is research-heavy (ingestion of one repo, not 20 files of it).
